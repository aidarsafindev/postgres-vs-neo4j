## Что такое граф

**Граф** — это математическая структура, состоящая из **вершин** (или **узлов**) и **рёбер**, которые их соединяют.

В обычной жизни графы встречаются повсюду:

- **Карта дорог** — города (узлы), дороги между ними (рёбра)
- **Социальная сеть** — люди (узлы), дружба (рёбра)
- **Цепочка поставок** — компании (узлы), поставки (рёбра)
- **Интернет** — страницы (узлы), ссылки (рёбра)
- **База знаний** — сущности (узлы), связи между ними (рёбра)

**Ключевая идея:** в графе важны не сами объекты, а **связи между ними**. Именно связи несут основную информацию.

## Три сущности графа

В графовой модели есть **три сущности**. Всё остальное — из них.

### 1. Узел (Node)

**Узел** — это объект предметной области.

Примеры:

- Город: Москва, Санкт-Петербург
- Склад: Склад Москва, Склад СПб
- Товар: Товар А, Товар B
- Человек: Иван, Мария
- Компания: ООО «Ромашка», ООО «Василёк»

У каждого узла есть **тип** (метка):

- `City` — город
- `Warehouse` — склад
- `Product` — товар
- `Person` — человек
- `Company` — компания

У каждого узла есть **свойства** (данные):

```cypher
(:City {name: 'Москва', population: 13000000})
(:Warehouse {name: 'Склад Москва', capacity: 10000})
(:Product {code: 'A001', name: 'Товар А'})
```

### 2. Ребро (Edge / Relationship)

**Ребро** — это связь между двумя узлами.

Примеры:

- Дорога: Москва → Санкт-Петербург
- Поставка: Склад Москва → Товар А
- Дружба: Иван → Мария
- Работа: Иван → ООО «Ромашка»

У каждого ребра есть **тип**:

- `ROAD` — дорога
- `STOCKS` — остатки
- `LOCATED_IN` — находится в
- `FRIEND` — друг
- `WORKS_AT` — работает в

У каждого ребра есть **направление** и **свойства**:

```cypher
(:City {name: 'Москва'})-[:ROAD {distance: 700, time_minutes: 240}]->(:City {name: 'Санкт-Петербург'})
(:Warehouse {name: 'Склад Москва'})-[:STOCKS {quantity: 100}]->(:Product {code: 'A001'})
```

**Важно:** ребро — это **самостоятельная сущность**. У него есть своё место в хранилище, свои свойства, свои индексы. Это не просто внешний ключ.

### 3. Свойство (Property)

**Свойство** — это данные, привязанные к узлу или к ребру.

На узле:

```cypher
(:City {name: 'Москва', population: 13000000})
        ↑                    ↑
     свойство             свойство
```

На ребре:

```cypher
[:ROAD {distance: 700, time_minutes: 240}]
        ↑                  ↑
     свойство           свойство
```

Свойства — это то, что отличает один узел от другого и одно ребро от другого.

## Что такое графовая база данных

**Графовая база данных** — это СУБД, которая хранит данные в виде графа: узлов, рёбер и свойств.

**Главное отличие от реляционной:**

| | Реляционная БД | Графовая БД |
|---|---|---|
| Единица хранения | Строка в таблице | Узел и ребро |
| Связь | Внешний ключ + JOIN | Ребро — самостоятельная сущность |
| Запрос связей | Вычисляет каждый раз | Читает готовое |
| Оптимизация | Под агрегаты и JOIN | Под обход графа |

**Ключевая идея:** реляционная база **вычисляет** связи через JOIN. Графовая база **хранит** связи как данные.

### Пример

**Реляционная модель:**

```sql
CREATE TABLE cities (id, name, population);
CREATE TABLE roads  (id, from_city_id, to_city_id, distance, time_minutes);
```

Связь между городами — это **число** `from_city_id`. Сама связь нигде не хранится. Каждый раз, когда нужно пройти по маршруту, база вычисляет её через JOIN.

**Графовая модель:**

```cypher
(:City {name: 'Москва'})-[:ROAD {distance: 700, time_minutes: 240}]->(:City {name: 'Санкт-Петербург'})
```

Связь `ROAD` — это **отдельная сущность**. У неё есть свойства (`distance`, `time_minutes`), она хранится в базе как самостоятельный объект. Когда нужно пройти по маршруту, база просто **читает** готовую связь.

## Что такое Neo4j

**Neo4j** — это самая популярная графовая СУБД. Работает с 2010 года.

### Основные характеристики

| Характеристика | Значение |
|---|---|
| Тип | Графовая СУБД (native graph) |
| Язык запросов | Cypher |
| Год выпуска | 2010 |
| Лицензия | GPLv3 (Community), Commercial (Enterprise) |
| Языки драйверов | Java, Python, .NET, JavaScript, Go, Rust |
| Протокол | Bolt (бинарный), HTTP |
| Хранение | Диск + RAM (pagecache) |

### Кто использует Neo4j

- **NASA** — граф знаний для миссий
- **Walmart** — рекомендации товаров
- **eBay** — логистика и маршрутизация
- **Cisco** — управление сетями
- **Airbnb** — граф доверия
- **Deutsche Bahn** — маршрутизация поездов
- **Microsoft** — GraphRAG для LLM

### Версии

| Версия | Что даёт |
|---|---|
| **Community** | Бесплатная. Single-node. Без кластера, без hot backup |
| **Enterprise** | Платная. Кластер, hot backup, ролевая модель |
| **AuraDB** | Облачная (managed) |

Для демо и пилота достаточно **Community**.

## Как работает Neo4j под капотом

### Хранение данных

Neo4j хранит узлы и рёбра **как указатели**, а не как строки в таблице.

**Реляционная БД:**

```
roads: id=1, from_city='Москва', to_city='СПб', distance=700
       id=2, from_city='Москва', to_city='Казань', distance=800
       ...
```

**Графовая БД:**

```
Node[Москва] → first_road → Road[700, 240] → next_road → Road[800, 300] → ...
Node[СПб]    ← first_road ← Road[700, 240]
```

Узел «Москва» **знает** свои рёбра. Не нужно ничего искать — они уже под рукой.

### Обход графа

Когда мы ищем кратчайший путь, Neo4j:

1. Берёт начальный узел
2. Читает его рёбра — мгновенно, потому что они уже связаны указателями
3. Переходит к соседним узлам
4. Повторяет, пока не найдёт целевой узел

**Сложность:** O(E + V log V), где E — число рёбер, V — число вершин. Линейный рост.

### Что под капотом у PostgreSQL

PostgreSQL вынужден:

1. Взять таблицу roads
2. Соединить её саму с собой (JOIN)
3. На каждом шаге — полное сканирование таблицы
4. Если маршрут длинный — экспоненциальный рост

**Сложность:** O(N^depth). Экспоненциальный рост.

### Почему граф быстрее

**Не потому что алгоритм лучше.** Алгоритм Дейкстры — тот же самый.

**А потому что данные лежат так, как нужно алгоритму.** Узел знает свои рёбра. Обход идёт напрямую, без JOIN.

Это не «Neo4j быстрее PostgreSQL». Это «графовая модель данных быстрее реляционной в задачах обхода связей».

## Cypher — язык запросов

**Cypher** — это декларативный язык запросов к графу. Аналог SQL для реляционных баз.

### Синтаксис

Cypher читается как **ASCII-арт**. Запросы выглядят как рисунки графа.

```
(a:City)-[r:ROAD]->(b:City)
 │         │           │
 узел     ребро       узел
```

- **Круглые скобки** `()` — узлы
- **Квадратные скобки** `[]` — рёбра
- **Стрелка** `->` — направление
- **Двоеточие** `:` — тип (метка)

Читается слева направо, как предложение: «из города A по дороге R в город B».

### Примеры запросов

**1. Найти все города:**

```cypher
MATCH (c:City)
RETURN c.name
```

**2. Найти кратчайший путь (с весами):**

```cypher
MATCH (from:City {name: 'Москва'}), (to:City {name: 'Новосибирск'})
CALL apoc.algo.dijkstra(from, to, 'ROAD>', 'time_minutes')
YIELD path, weight
RETURN [n IN nodes(path) | n.name] AS cities, weight
```

**3. Найти цепочку на 5 уровней:**

```cypher
MATCH path = (p:Product {code: 'A001'})<-[:STOCKS*1..5]-(w:Warehouse)
RETURN w.name, length(path)
```

**4. Найти рекомендации:**

```cypher
MATCH (p:Product {code: 'A001'})-[bw:BOUGHT_WITH]->(rec)
RETURN rec.code, bw.frequency
ORDER BY bw.frequency DESC
LIMIT 5
```

**5. Обновить данные:**

```cypher
MERGE (a:City {name: 'Москва'})
MERGE (b:City {name: 'Казань'})
MERGE (a)-[r:ROAD]->(b)
SET r.distance = 800, r.time_minutes = 300
```

### Ключевые команды

| Команда | Что делает |
|---|---|
| `MATCH` | Найти узлы и рёбра по шаблону |
| `WHERE` | Фильтр |
| `RETURN` | Вернуть результат |
| `CREATE` | Создать узел или ребро |
| `MERGE` | Найти или создать (идемпотентно) |
| `SET` | Установить свойство |
| `DELETE` | Удалить |
| `WITH` | Промежуточный шаг |
| `UNWIND` | Развернуть список в строки |
| `CALL` | Вызвать процедуру (например, APOC) |

## PostgreSQL vs Neo4j — сравнение

### Общее сравнение

| Критерий | PostgreSQL | Neo4j |
|---|---|---|
| Тип | Реляционная | Графовая |
| Единица хранения | Строка | Узел и ребро |
| Связь | Внешний ключ + JOIN | Ребро — самостоятельная сущность |
| Язык | SQL | Cypher |
| Транзакции | ACID | ACID |
| Индексы | B-tree, GIN, GiST | B-tree, full-text, vector |
| Масштабирование | Вертикальное + реплики | Вертикальное + кластер (Enterprise) |
| Экосистема | Огромная | Меньше, но растёт |

### Производительность на разных задачах

| Задача | PostgreSQL | Neo4j |
|---|---|---|
| Агрегаты по периодам | ✅ Отлично | ⚠️ Средне |
| Отчёты с GROUP BY | ✅ Отлично | ⚠️ Средне |
| Транзакции (OLTP) | ✅ Отлично | ⚠️ Медленнее запись |
| Обход связей на глубину 3+ | ❌ Медленно | ✅ Отлично |
| Кратчайший путь | ❌ Медленно | ✅ Отлично |
| Цепочки поставок | ❌ Медленно | ✅ Отлично |
| Рекомендации | ❌ Медленно | ✅ Отлично |
| Полнотекстовый поиск | ✅ Отлично | ⚠️ Средне |
| Векторный поиск | ⚠️ Через pgvector | ✅ Встроен в Neo4j 5 |

### Когда что использовать

**PostgreSQL:**

- Документы, проводки, регистры
- Отчёты и агрегаты
- Транзакционная запись
- Источник истины

**Neo4j:**

- Обход связей на глубину 3+
- Кратчайший путь
- Цепочки поставок
- Рекомендации
- Антифрод
- Граф знаний

**Правило:** если задача про **обход связей** — Neo4j. Если про **агрегаты и учёт** — PostgreSQL.

## Где применяется Neo4j

### 1. Логистика и маршрутизация

- Кратчайший путь с учётом пробок
- Оптимизация маршрутов доставки
- Управление парком машин

**Пример:** 500 заказов, 50 складов, 200 машин. Было 45 минут на расчёт. Стало 200 миллисекунд.

### 2. Цепочки поставок

- Кто поставил этот товар?
- Кто поставил поставщика?
- Где узкие места в цепочке?

**Пример:** найти всех поставщиков товара до 5-го уровня — одна строка Cypher.

### 3. Рекомендации

- Что покупают вместе с этим?
- Кто похож на этого пользователя?
- Какие товары часто покупают вместе?

**Пример:** рёбра `BOUGHT_WITH` с весом — обход соседей узла.

### 4. Антифрод

- Поиск циклов в транзакциях
- Выявление связанных мошеннических счетов
- PageRank для поиска «важных» узлов

**Пример:** цикл из 3–7 транзакций с крупными суммами — классическая схема отмывания.

### 5. Master Data Management

- Связи контрагентов через директоров
- Общие адреса и счета
- Кластеры связанных компаний

**Пример:** «Найди все компании, связанные через общего директора» — один запрос.

### 6. Управление доступами

- Граф ролей и ресурсов
- «Какие документы доступны пользователю через группы?»
- Проверка доступа — обход графа

**Пример:** пользователь → группа → роль → ресурс. Один запрос вместо десятка JOIN.

### 7. GraphRAG для LLM

- Граф знаний для языковых моделей
- Ответы на вопросы «кто с кем связан»
- Векторный индекс в Neo4j 5

**Пример:** база знаний по типовым конфигурациям 1С.

## Ограничения и подводные камни

**Быстрое чтение не даётся бесплатно.** У Neo4j есть свои ограничения.

### 1. Запись медленнее, чем чтение

Neo4j оптимизирован под **обход графа**. Но **вставка узлов и рёбер** — дороже, чем в PostgreSQL.

**Почему:**

- Каждое ребро — это две ссылки (от узла A к узлу B и обратно)
- Индексы обновляются при каждой вставке
- Транзакции требуют больше служебных данных

**Что это значит на практике:**

- Массовая загрузка — только через `neo4j-admin import` или батчи через `UNWIND`
- В демо: 100 000 городов генерируются **минуты**, не секунды
- Для транзакционной записи — PostgreSQL остаётся лучше

### 2. Память — критичный ресурс

Графы **живут в RAM**. Pagecache должен вмещать граф — иначе обход пойдёт на диск.

**Что это значит:**

- 1 млн узлов ≈ 1 ГБ RAM
- 10 млн узлов ≈ 8 ГБ RAM
- 100 млн узлов ≈ 64+ ГБ RAM

**Правило:** если граф не влезает в память — скорость падает в разы.

**Что делать:**

- Планировать инфраструктуру заранее
- Использовать `pagecache` настроенный под размер графа
- Для очень больших графов — шардирование по домену (география, бизнес-единица)

### 3. Дублирование данных

Neo4j — **вторая база**. PostgreSQL остаётся источником истины. Значит, данные надо **синхронизировать**.

**Что это значит:**

- Нет «бесплатной» консистентности
- Возможен рассинхрон на секунды
- Нужен reconciliation — регулярная сверка
- Дополнительный код, дополнительный on-call

**Что делать:**

- Eventual consistency как осознанный выбор
- Reconciliation job раз в час
- Логирование расхождений в Grafana
- При критичных расхождениях — полная пересинхронизация

### 4. Экосистема меньше

**Специалистов** по Neo4j меньше, чем по PostgreSQL. **Инструментов** для бэкапов, миграций, мониторинга — тоже меньше.

**Что это значит:**

- Обучение команды — обязательно
- Меньше готовых решений — больше своего кода
- Меньше Stack Overflow — больше документации

**Что делать:**

- Начать с пилота на одной задаче
- Не внедрять сразу в прод
- Обучить 2–3 человек на команду
- Использовать официальную документацию и курсы Neo4j

### 5. Cypher — отдельный язык

Cypher — это **не SQL**. Его надо учить, как когда-то SQL.

**Что это значит:**

- Команда не может «просто начать писать»
- Первые запросы будут неоптимальными
- Нужны 2–3 недели на базовый уровень

**Что делать:**

- Выделить время на обучение
- Использовать `PROFILE` для анализа запросов
- Не бояться переписывать запросы после первых прогонов

### 6. Не замена PostgreSQL

**Главное:** Neo4j — не замена PostgreSQL. Это **второй инструмент в арсенале**.

**Что это значит:**

- Учёт — в PostgreSQL
- Графовые задачи — в Neo4j
- Синхронизация между ними
- Две СУБД — два мониторинга, два бэкапа

**Правило:** если задача не про связи — не тащите Neo4j. Платить сложностью не за что.

## Когда Neo4j НЕ нужен

### 1. Данных мало

**Если у вас < 10 000 узлов** — PostgreSQL справится за миллисекунды. Граф не даст выигрыша.

### 2. Задача не про связи

**Если задача про агрегаты и отчёты** — Neo4j не поможет. Он оптимизирован под обход графа, а не под GROUP BY.

### 3. Нет ресурсов на вторую СУБД

**Если команда не может поддерживать две СУБД** — не берите Neo4j. Один инструмент — одна точка отказа, но и одна точка компетенции.

### 4. Команда не готова изучать Cypher

**Если нет времени на обучение** — не берите Neo4j. Плохой Cypher-запрос хуже хорошего SQL-запроса.

### 5. Связи простые

**Если связи на 1–2 уровня** — SQL справится. Граф выигрывает на глубине 3+.

### Правило трёх «НЕ»

1. **НЕ** внедряйте Neo4j, если PostgreSQL справляется
2. **НЕ** дублируйте все данные в граф — только связи
3. **НЕ** пытайтесь заменить реляционный учёт графом

**PostgreSQL + Neo4j — это не «или», а «и».**

## Глоссарий

### Узел (Node)

Объект предметной области. Имеет тип (метку) и свойства.

**Пример:** `(:City {name: 'Москва', population: 13000000})`

### Ребро (Edge / Relationship)

Связь между двумя узлами. Имеет тип, направление и свойства.

**Пример:** `[:ROAD {distance: 700, time_minutes: 240}]`

### Свойство (Property)

Данные, привязанные к узлу или ребру.

**Пример:** `name`, `population`, `distance`, `time_minutes`

### Метка (Label)

Тип узла.

**Пример:** `City`, `Warehouse`, `Product`

### Cypher

Язык запросов к графу в Neo4j. Аналог SQL.

### APOC

Библиотека процедур для Neo4j. Расширяет стандартный Cypher. Содержит `apoc.algo.dijkstra` и другие алгоритмы.

### GDS (Graph Data Science)

Библиотека алгоритмов для Neo4j. PageRank, Louvain, betweenness и другие.

### Dijkstra

Алгоритм поиска кратчайшего пути во взвешенном графе. Работает за O(E + V log V).

### PageRank

Алгоритм оценки важности узлов в графе. Используется в антифроде.

### Louvain

Алгоритм поиска сообществ в графе. Используется для кластеризации.

### Bolt

Бинарный протокол для связи с Neo4j. Быстрее HTTP.

### Pagecache

Кэш графа в RAM. Критичен для производительности.

### Eventual consistency

Модель согласованности, при которой данные обновляются асинхронно. Граф обновляется чуть позже, но обязательно.

### Reconciliation

Процесс сверки данных между двумя источниками (PostgreSQL и Neo4j).

### GraphRAG

Подход к построению RAG-систем, использующий граф знаний. Комбинация векторного поиска и обхода связей.
