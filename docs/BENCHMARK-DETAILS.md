# Детальная расшифровка бенчмарка

Одна задача: найти кратчайший путь между двумя городами. Четыре способа её решить. Этот документ объясняет, откуда берутся цифры и что означает каждый разрыв.

## Итоговая таблица

| Объём | SQL naive | SQL + pruning | pgRouting | Neo4j |
|---|---|---|---|---|
| 100 городов | 2 с | 50 мс | 5 мс | 1 мс |
| 1 000 | 15 с | 500 мс | 20 мс | 2 мс |
| 10 000 | 3 мин | 5 с | 200 мс | 3 мс |
| 100 000 | 45 мин | 3 мин | 800 мс | 5 мс |

**Что показывает таблица:**

- **SQL naive vs SQL optimized** — 3000× — цена отсутствия pruning
- **SQL optimized vs pgRouting** — 200× — цена эмуляции графа в реляционной модели
- **pgRouting vs Neo4j** — 4–5× — цена SQL-обвязки и round-trip
- **SQL naive vs Neo4j** — 13 500× — итоговый разрыв

**Цифры — заглушки.** Запустите бенчмарк на своём железе:

```bash
bash scripts/run-benchmark.sh
```

## Четыре варианта — зачем

| Вариант | Что показывает | Аналогия |
|---|---|---|
| SQL naive | Как пишут «в лоб» | Ехать на велосипеде |
| SQL optimized | Что даёт честная оптимизация | Ехать на машине |
| pgRouting | Предел PostgreSQL для графов | Ехать на спортивной машине |
| Neo4j | Предел графовой модели | Ехать на поезде |

Каждая пара соседних вариантов отвечает на свой вопрос. Четыре точки — четыре вывода.

## Вариант 1. SQL naive — 45 минут

### Что это

Рекурсивный CTE, который обходит **все** возможные пути до глубины 10, не отбрасывая заведомо длинные.

```sql
WITH RECURSIVE paths AS (
    SELECT
        r.to_city_id,
        ARRAY[r.from_city_id, r.to_city_id] AS path,
        r.time_minutes AS total_weight,
        1 AS hops
    FROM roads r
    WHERE r.from_city_id = 1

    UNION ALL

    SELECT
        r.to_city_id,
        p.path || r.to_city_id,
        p.total_weight + r.time_minutes,
        p.hops + 1
    FROM paths p
    JOIN roads r ON p.to_city_id = r.from_city_id
    WHERE NOT r.to_city_id = ANY(p.path)   -- циклы
      AND p.hops < 10                       -- глубина
)
SELECT path, total_weight, hops
FROM paths
WHERE to_city_id = 4
ORDER BY total_weight ASC
LIMIT 1;
```

### Почему медленно

| Причина | Пояснение |
|---|---|
| Нет pruning | Идём по всем путям, даже если вес уже превышает оптимум |
| Экспонента | Количество путей — O(N^depth) |
| Temp-файлы | Сортировка миллионов строк не влезает в память |
| Проверка циклов | `NOT r.to_city_id = ANY(p.path)` — O(depth) на шаге |

### Что показывает

Так пишут SQL «в лоб». Это не предел PostgreSQL, это **нижняя граница**. Именно этот код даёт «45 минут» на слайде 2.

**Реалистичность:** в продакшене такой код встречается чаще, чем хотелось бы.

**Файл:** `sql/benchmark-queries.sql`, вариант 1.

## Вариант 2. SQL + pruning — 3 минуты

### Что это

Тот же рекурсивный CTE, но с **отсечением по весу**. Одна строчка меняет всё:

```sql
WHERE NOT r.to_city_id = ANY(p.path)
  AND p.hops < 10
  AND p.total_weight + r.time_minutes < 10000   -- ← вот эта строка
```

### Почему быстрее в 15 раз

| Причина | Пояснение |
|---|---|
| Отсечение по весу | Путь длиннее оптимума — не продолжаем |
| Меньше строк | Из миллиона путей отбрасываются 99% |
| Индексы | `(from_city_id, time_minutes)` — быстрый поиск рёбер |
| ANALYZE | Планировщик знает реальную статистику |

### Что показывает

Даже честная оптимизация SQL не спасает. 3 минуты против 45 — прогресс, но всё ещё **минуты**.

**Вывод:** SQL можно писать хорошо или плохо. Разница — 15 раз. Но и хороший SQL проигрывает нативному алгоритму.

**Файл:** `sql/postgres-schema.sql` — функция `shortest_path_sql`.

## Вариант 3. pgRouting — 800 миллисекунд

### Что это

Расширение PostgreSQL, реализующее алгоритм Дейкстры **на C**. Не SQL-эмуляция, а нативный код внутри той же базы.

```sql
CREATE EXTENSION IF NOT EXISTS pgrouting;

SELECT * FROM pgr_dijkstra(
    'SELECT id, from_city_id AS source, to_city_id AS target,
            time_minutes AS cost FROM roads',
    1,   -- Москва
    4,   -- Новосибирск
    directed := false
);
```

### Почему быстрее в 200 раз

| Причина | Пояснение |
|---|---|
| Нативный алгоритм | O(E + V log V) вместо O(N^depth) |
| Нет recursive CTE | Нет миллионов промежуточных строк |
| Нет сортировки | Алгоритм сразу выдаёт кратчайший путь |
| Те же данные | Не нужно ничего переносить |

### Что показывает

PostgreSQL **может** быстро считать графы — если использовать правильный инструмент.

**Это самая честная точка сравнения.** Если скептик говорит «дайте мне pgRouting» — вот ответ.

**Почему не основной инструмент:**

- Менее выразительный, чем Cypher
- Требует ручной подготовки графа (source / target / cost)
- Не подходит для рекомендаций и цепочек поставок «из коробки»

**Файл:** `sql/benchmark-queries.sql`, вариант 3.

## Вариант 4. Neo4j — 5 миллисекунд

### Что это

`apoc.algo.dijkstra` — тот же алгоритм Дейкстры, но в графовой БД, где рёбра хранятся как указатели, а не как строки в таблице.

```cypher
MATCH (from:City {name: 'Москва'}), (to:City {name: 'Новосибирск'})
CALL apoc.algo.dijkstra(from, to, 'ROAD>', 'time_minutes')
YIELD path, weight
RETURN [n IN nodes(path) | n.name] AS cities,
       weight AS total_weight,
       length(path) AS hops;
```

### Почему быстрее pgRouting в 4–5 раз

| Причина | Пояснение |
|---|---|
| Нет SQL-обвязки | Нет парсинга, планировщика, JOIN-ов |
| Указатели вместо строк | Узел знает свои рёбра — обход напрямую |
| Данные под алгоритм | Не нужно перестраивать граф |
| Индексы на узлах | Мгновенный старт |

**Важно:** это не алгоритмическое преимущество. Алгоритм тот же — Дейкстра. Это преимущество **модели данных**.

### Что НЕ используем

```cypher
-- ❌ НЕ используем: shortestPath считает по числу хопов, а не по весам
MATCH path = shortestPath((from:City)-[:ROAD*]->(to:City))
RETURN path
```

`shortestPath` — это BFS. Для весов нужен `apoc.algo.dijkstra` или `gds.shortestPath.dijkstra`.

**Файл:** `src/proxy/app.py` — эндпоинт `/api/v1/graph/shortest-path`.

## Разрывы — что они значат

### SQL naive → SQL + pruning: 3000×

| Параметр | Значение |
|---|---|
| Формула | 45 мин / 3 мин ≈ 15 на 100 000 |
| Что это | Цена отсутствия pruning |
| Смысл | SQL можно писать хорошо или плохо |
| Что запомнить | Наивный SQL — нижняя граница, не предел PostgreSQL |

### SQL + pruning → pgRouting: 200×

| Параметр | Значение |
|---|---|
| Формула | 3 мин / 800 мс ≈ 225 на 100 000 |
| Что это | Цена эмуляции графа в реляционной модели |
| Смысл | Pruning помогает, но не отменяет модель |
| Что запомнить | Эмуляция графа в SQL имеет потолок |

### pgRouting → Neo4j: 4–5×

| Параметр | Значение |
|---|---|
| Формула | 800 мс / 5 мс ≈ 160 на 100 000 |
| Что это | Цена SQL-обвязки и round-trip |
| Смысл | Алгоритм тот же — Дейкстра. Модель данных — разная |
| Что запомнить | **Самая честная цифра в таблице** |

**Это инженерная цифра.** Если скептик скажет «дайте мне pgRouting» — вот ответ.

### SQL naive → Neo4j: 13 500×

| Параметр | Значение |
|---|---|
| Формула | 45 мин / 200 мс ≈ 13 500 на демо-графе |
| Что это | Итоговый разрыв в задаче |
| Смысл | Наивный SQL — то, что пишут в проде. Neo4j — то, что «из коробки» |
| Что запомнить | **Это маркетинговая цифра.** Работает на слайде, не должна быть основой решения |

## Шпаргалка: что говорить

### Ключевые фразы

1. «Все цифры — заглушки. Реальные зависят от железа, данных, индексов. Репозиторий — чтобы проверить.»

2. «Три варианта SQL — это честность. Не „SQL плохой", а „вот три способа, вот их цена".»

3. «Разрыв pgRouting vs Neo4j — 4–5× — это и есть истина. Остальные разрывы — про то, как не надо и как надо писать SQL.»

4. «Даже лучший SQL (pgRouting) проигрывает Neo4j. Но не в 13 500 раз, а в 4–5. И вот в каких случаях эти 4–5 раз критичны: миллисекунды против миллисекунд, а не минуты против минут.»

### Одна фраза для зала

> «Наивный SQL vs Neo4j — 13 500 раз. Это цифра для слайда. pgRouting vs Neo4j — 4–5 раз. Это цифра для архитектурного решения. Первая — маркетинг. Вторая — инженерия.»

### Пауза

Дать залу 5–10 секунд, чтобы рассмотреть таблицу. Это ключевой слайд доклада.

## Как воспроизвести

### 1. Поднять стенд

```bash
git clone https://github.com/yourname/postgres-vs-neo4j.git
cd postgres-vs-neo4j
cp .env.example .env
docker-compose up -d
```

### 2. Инициализировать данные

```bash

bash scripts/init-graph.sh
bash scripts/init-db.sh

# Большой граф (100 000 городов)
NUM_CITIES=100000 NUM_ROADS=500000 \
  docker-compose --profile generator run --rm generator
```

### 3. Запустить бенчмарк

```bash
bash scripts/run-benchmark.sh
```

## Ограничения бенчмарка

| Чего НЕТ | Что это значит |
|---|---|
| Materialized views | Цифры — нижняя граница для SQL |
| Partitioning roads | Реальный SQL может быть быстрее |
| Кэширование | Повторные запросы не оптимизированы |
| Кластер Neo4j | Single-node в демо |
| Реальные пробки | Синтетические данные |
| Разные типы рёбер | Только ROAD |
| Свойства на рёбрах | Только distance и time |

**Вывод:** цифры — нижняя граница для SQL и верхняя для Neo4j. Реальный разрыв может быть меньше. Но даже так — он на порядки.
