## Зачем этот документ

Графы — для **всего, где связи важнее самих объектов**. Этот документ показывает четыре области, где та же модель данных решает ту же задачу — обход связей — но в другом контексте.

**Общий принцип:** один инструмент, одна модель, четыре предметные области.

---

## Глоссарий

Прежде чем разбирать сценарии — термины.

### GraphRAG

**Определение:** подход к построению RAG-систем (Retrieval-Augmented Generation), в котором источником контекста для языковой модели служит не набор документов, а **граф знаний**. Аббревиатура от *Graph Retrieval-Augmented Generation*.

**Зачем:** обычный RAG ищет похожие по вектору фрагменты текста. GraphRAG умеет отвечать на вопросы «кто с кем связан», «как A связано с B через 3 звена», «какие сущности упоминаются вместе».

**В контексте 1С:** база знаний по типовым конфигурациям. «Как связаны документ, регистр и отчёт», «почему эта проводка не формируется».

---

### Knowledge Graph (граф знаний)

**Определение:** граф, где узлы — сущности предметной области (люди, компании, документы, товары), а рёбра — типизированные связи между ними (работает в, поставщик для, упоминается в).

**Отличие от обычного графа:** рёбра имеют **семантику**. Не просто «связаны», а «как именно связаны».

**В контексте 1С:** справочники и регистры — это уже граф знаний, просто хранятся в таблицах.

---

### Vector index (векторный индекс)

**Определение:** структура данных для быстрого поиска похожих векторов. Позволяет за миллисекунды найти ближайшие соседи в многомерном пространстве.

**В контексте Neo4j 5:** встроенный `VECTOR INDEX` позволяет хранить эмбеддинги прямо в узлах и искать по ним вместе с обходом связей. Это ключевая фича для GraphRAG.

**Аналогия:** обычный индекс ищет по точному значению. Векторный — по смыслу.

---

### PageRank

**Определение:** алгоритм оценки важности узлов в графе, изначально придуманный Google для ранжирования веб-страниц. Узел тем важнее, чем больше важных узлов на него ссылаются.

**В контексте Neo4j:** `gds.pageRank.stream` — готовая процедура в Graph Data Science. Работает на графе транзакций, связей контрагентов, любых отношений «кто на кого ссылается».

**Зачем в антифроде:** выявляет подозрительно «важные» узлы — например, счета, через которые проходят цепочки платежей.

---

### Community detection (поиск сообществ)

**Определение:** класс алгоритмов, которые находят плотные группы узлов в графе. Классический — Louvain.

**В контексте Neo4j:** `gds.louvain.stream` — находит сообщества в графе. В антифроде — группы связанных мошеннических счетов. В MDM — кластеры компаний, связанных через общих директоров.

---

### MDM (Master Data Management)

**Определение:** дисциплина управления справочными данными. Задача — свести дубли и построить единый «золотой» профиль сущности (клиента, контрагента, товара).

**В контексте 1С:** `Справочник.Контрагенты` + `РегистрСведений.КонтактныеЛица`. Если два контрагента связаны через одного директора — это может быть одна и та же компания.

**Почему граф:** связи между контрагентами — это естественно граф. В SQL — это self-join таблицы, которая растёт экспоненциально.

---

### RBAC / ABAC

**Определение:**
- **RBAC** (Role-Based Access Control) — доступ определяется ролью пользователя.
- **ABAC** (Attribute-Based Access Control) — доступ определяется атрибутами пользователя, ресурса и контекста.

**В контексте графа:** и роли, и атрибуты — это узлы. Связи «роль → ресурс», «пользователь → роль», «группа → пользователь» — это рёбра. Запрос «какие документы доступны пользователю через группы» — обход графа.

---

### Centrality (центральность)

**Определение:** мера важности узла в графе. PageRank — один из видов. Другие: betweenness (сколько кратчайших путей проходит через узел), degree (сколько связей у узла).

**Зачем:** в антифроде — выявить «мосты» между группами мошенников. В MDM — найти ключевых связующих лиц.

## GraphRAG для LLM

### Проблема

Обычный RAG (Retrieval-Augmented Generation) работает так:

1. Пользователь задаёт вопрос
2. Система ищет **похожие по вектору** фрагменты текста
3. Отдаёт их языковой модели как контекст
4. Модель генерирует ответ

**Что не работает:**

- «Кто с кем связан» — векторный поиск не видит связей, только похожесть
- «Как A связано с B через 3 звена» — модель не может пройти по цепочке
- «Какие сущности упоминаются вместе» — это структурный запрос, а не поиск похожести

### Решение: GraphRAG

GraphRAG добавляет к векторному поиску **граф знаний**:

1. Документы разбиваются на фрагменты
2. Из фрагментов извлекаются сущности (люди, компании, термины)
3. Строится граф: сущности — узлы, совместные упоминания — рёбра
4. Каждый узел получает эмбеддинг (vector index)
5. Запрос ищет похожие узлы **и** обходит их связи

### Пример запроса

```cypher
// Найти документы, связанные с вопросом пользователя,
// и сущности, которые упоминаются вместе с ними
MATCH (d:Document)-[:MENTIONS]->(e:Entity)
WHERE e.embedding <-> $query_embedding < 0.3
MATCH path = (e)-[:RELATED*1..3]-(related:Entity)
RETURN d.title, related.name, path
ORDER BY length(path)
LIMIT 10
```

**Что здесь важно:** `e.embedding <-> $query_embedding` — векторный поиск. `(e)-[:RELATED*1..3]-(related)` — обход связей. Обычный RAG умеет только первое.

### Применение в 1С

**Сценарий:** база знаний по типовым конфигурациям.

**Вопрос пользователя:** «Почему не формируется проводка по документу РеализацияТоваровУслуг?»

**GraphRAG-ответ:**

1. Векторный поиск находит документы, похожие на вопрос
2. Обход графа находит связанные сущности: регистр, проводку, настройку учётной политики
3. Модель получает контекст: «РеализацияТоваровУслуг» → «РегистрБухгалтерии.Хозрасчетный» → «НастройкаУчетнойПолитики»
4. Генерируется ответ: «Проводка не формируется, потому что в настройках учётной политики не указан счёт для реализации услуг»

**Что даёт граф:** модель видит **структуру** базы знаний, а не просто похожие фрагменты.

### Стек

| Компонент | Роль |
|---|---|
| Neo4j 5 | Хранение графа + vector index |
| LLM (GigaChat, YandexGPT, GPT-4) | Извлечение сущностей, генерация ответа |
| Embedding model | Векторизация узлов |
| API-прокси | Интеграция с 1С |

## Антифрод

### Проблема

**Задача:** найти мошеннические схемы в графе транзакций.

**Что ищем:**

- Цепочки платежей через промежуточные счета
- Группы связанных счетов (сообщества)
- Счета-«мосты» между группами
- Циклы в цепочках поставок (отмывание)

**Почему SQL плохо:**

- Граф транзакций — миллионы рёбер
- «Найти цепочку A → B → C → A» в SQL — рекурсивный CTE на миллионах строк
- «Найти сообщества» — вообще не выражается в SQL без специальных расширений

### Решение: алгоритмы на графе

**1. PageRank — найти важные счета**

```cypher
CALL gds.pageRank.stream('transaction-graph')
YIELD nodeId, score
RETURN gds.util.asNode(nodeId).account_id AS account, score
ORDER BY score DESC
LIMIT 20
```

Счета с высоким PageRank — через них проходят цепочки. Не обязательно мошеннические, но требуют внимания.

**2. Louvain — найти сообщества**

```cypher
CALL gds.louvain.stream('transaction-graph')
YIELD nodeId, communityId
RETURN communityId, collect(gds.util.asNode(nodeId).account_id) AS accounts
```

Сообщества — группы счетов, которые активно взаимодействуют между собой. Если группа замкнута и изолирована — это подозрительно.

**3. Поиск циклов — отмывание**

```cypher
MATCH path = (a:Account)-[:TRANSFER*3..7]->(a)
WHERE ALL(r IN relationships(path) WHERE r.amount > 100000)
RETURN path, length(path)
LIMIT 10
```

Цикл из 3–7 транзакций с крупными суммами — классическая схема отмывания.

**4. Centrality — найти мосты**

```cypher
CALL gds.betweenness.stream('transaction-graph')
YIELD nodeId, score
RETURN gds.util.asNode(nodeId).account_id AS account, score
ORDER BY score DESC
LIMIT 10
```

Узлы с высокой betweenness — «мосты» между группами. Часто это транзитные счета.

### Применение в 1С

- Граф транзакций из `Документ.ПлатёжноеПоручение`
- Связи контрагентов из `Справочник.Контрагенты`
- Ежедневный прогон GDS-алгоритмов
- Уведомления в 1С через API

### Стек

| Компонент | Роль |
|---|---|
| Neo4j + GDS | Хранение графа + алгоритмы |
| ETL из PostgreSQL | Синхронизация транзакций |
| Планировщик | Ежедневный прогон |
| 1С | UI и уведомления |

## Master Data Management

### Проблема

**Задача:** свести дубли контрагентов в единый «золотой» профиль.

**Что мешает:**

- Один контрагент заведён трижды с разными названиями
- Разные юрлица связаны через одного директора
- Один адрес используется десятью компаниями
- Один банковский счёт у нескольких контрагентов

**Почему SQL плохо:**

- Self-join таблицы контрагентов — экспоненциальный рост
- «Найти все компании, связанные через общего директора» — рекурсивный CTE
- «Найти транзитивные связи» — глубина неизвестна

### Решение: граф связей

**Модель данных:**

```cypher
(Company)-[:HAS_DIRECTOR]->(Person)
(Company)-[:LOCATED_AT]->(Address)
(Company)-[:HAS_ACCOUNT]->(BankAccount)
(Company)-[:HAS_PHONE]->(Phone)
(Company)-[:HAS_EMAIL]->(Email)
(Person)-[:WORKS_AT]->(Company)
```

**Запрос 1: компании через общего директора**

```cypher
MATCH (c1:Company)-[:HAS_DIRECTOR]->(p:Person)<-[:HAS_DIRECTOR]-(c2:Company)
WHERE c1 <> c2
RETURN c1.name, c2.name, p.name AS shared_director
```

**Запрос 2: транзитивные связи до 3 шагов**

```cypher
MATCH path = (c1:Company)-[:HAS_DIRECTOR|LOCATED_AT|HAS_ACCOUNT*1..3]-(c2:Company)
WHERE c1.id < c2.id
RETURN c1.name, c2.name, length(path) AS distance, path
ORDER BY distance
```

**Запрос 3: кластеры связанных компаний**

```cypher
CALL gds.louvain.stream('company-graph')
YIELD nodeId, communityId
RETURN communityId, collect(gds.util.asNode(nodeId).name) AS companies
```

**Что даёт граф:** за один запрос — все связи, включая транзитивные. В SQL это был бы рекурсивный CTE на миллионах строк.

### Применение в 1С

- `Справочник.Контрагенты` — узлы
- `РегистрСведений.КонтактныеЛица` — рёбра HAS_DIRECTOR
- `Справочник.Адреса` — узлы Address
- Ежедневная синхронизация в Neo4j
- Отчёт «Подозрительные связи» в 1С

### Стек

| Компонент | Роль |
|---|---|
| Neo4j | Хранение графа связей |
| ETL | Синхронизация справочников |
| GDS | Louvain для кластеров |
| 1С | UI для MDM-специалиста |

## Управление доступами

### Проблема

**Задача:** ответить на вопрос «какие документы доступны пользователю?»

**Сложности:**

- Пользователь входит в несколько групп
- Группы вложены друг в друга
- Роли наследуются
- Ресурсы связаны иерархически
- Правила наследуются по цепочке

**Почему SQL плохо:**

- Иерархия групп — рекурсивный CTE
- «Найти все ресурсы через все группы пользователя» — множественный JOIN
- «Проверить, есть ли путь от пользователя к ресурсу» — обход графа

### Решение: граф доступов

**Модель данных:**

```cypher
(User)-[:MEMBER_OF]->(Group)
(Group)-[:MEMBER_OF]->(Group)         // вложенность
(Group)-[:HAS_ROLE]->(Role)
(Role)-[:CAN_ACCESS]->(Resource)
(Resource)-[:PARENT_OF]->(Resource)   // иерархия
```

**Запрос 1: все ресурсы пользователя**

```cypher
MATCH (u:User {login: $login})-[:MEMBER_OF*1..5]->(g:Group)
      -[:HAS_ROLE]->(r:Role)-[:CAN_ACCESS]->(res:Resource)
RETURN DISTINCT res.name, g.name, r.name
```

**Запрос 2: есть ли путь от пользователя к ресурсу**

```cypher
MATCH path = shortestPath(
    (u:User {login: $login})-[:MEMBER_OF|HAS_ROLE|CAN_ACCESS*1..10]->(res:Resource {id: $res_id})
)
RETURN path, length(path)
```

**Запрос 3: кто имеет доступ к ресурсу**

```cypher
MATCH (u:User)-[:MEMBER_OF*1..5]->(g:Group)
      -[:HAS_ROLE]->(r:Role)-[:CAN_ACCESS]->(res:Resource {id: $res_id})
RETURN DISTINCT u.login, g.name, r.name
```

**Что даёт граф:** проверка доступа — это обход графа. Один запрос вместо десятка JOIN.

### Применение в 1С

- `Справочник.Пользователи` — узлы User
- `Справочник.ГруппыПользователей` — узлы Group
- `Справочник.Роли` — узлы Role
- `ПланВидовХарактеристик.ВидыДоступа` — узлы Resource
- Синхронизация через API при изменении прав
- Проверка доступа через прокси

**Важно:** не замена штатной подсистемы прав 1С, а **дополнительный** инструмент для сложных аудитов.

| Компонент | Роль |

| API-прокси | Проверка доступа |
| 1С | UI и интеграция |

## Что общего у четырёх сценариев

| Сценарий | Узлы | Рёбра | Что ищем |
|---|---|---|---|
| GraphRAG | Документы, сущности | MENTIONS, RELATED | Связи сущностей для контекста LLM |
| Антифрод | Счета, контрагенты | TRANSFER, OWNS | Цепочки, сообщества, циклы |
| MDM | Компании, люди, адреса | HAS_DIRECTOR, LOCATED_AT | Транзитивные связи, кластеры |
| Доступы | Пользователи, группы, ресурсы | MEMBER_OF, CAN_ACCESS | Путь от пользователя к ресурсу |

**Общий принцип:** во всех четырёх задачах **связи важнее самих объектов**. SQL умеет хранить объекты, но связи в нём — это вычисляемые JOIN-ы. Граф хранит связи как данные.

**Общий признак:** если задача формулируется через «найти путь», «найти цепочку», «найти связанные», «найти сообщества» — это задача для графа.

## Что говорить при показе слайда

### Ключевые фразы

1. «Логистика — это только начало. Тот же инструмент, та же модель — четыре другие области.»

2. «**GraphRAG для LLM** — это сейчас самая горячая тема на стыке графов и ИИ. Neo4j 5 получил встроенный vector index, и это меняет правила игры для RAG-систем.»

3. «**Антифрод** — PageRank и Louvain на графе транзакций. В SQL это не выражается без специальных расширений.»

4. «**Master Data Management** — связи контрагентов через директоров, адреса, счета. В 1С это `Справочник.Контрагенты` плюс `РегистрСведений.КонтактныеЛица`. Естественный граф.»

5. «**Управление доступами** — граф ролей и ресурсов. Проверка доступа — это обход графа. Один запрос вместо десятка JOIN.»

### Одна фраза для зала

> «Один инструмент, одна модель — четыре предметные области. Если задача формулируется через „найти связанные" или „найти путь" — это задача для графа.»

### Пауза

Дать залу 5–10 секунд, чтобы рассмотреть четыре колонки. Не углубляться — тезисно.
